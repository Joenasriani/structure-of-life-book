P. 05
WHY THIS BOOK EXISTS

Life presents the inverse problem.

Engineers are trained to turn difficult things into inspectable structure. They identify states, constraints, dependencies, interfaces, feedback, memory, error and change. The vocabulary is explicit because the system must eventually run.

Life usually gives us the opposite situation. We did not design the system. We see outputs, fragments of state and partial histories, then try to infer the rules.

Before solving a problem, see its structure. Before trusting the structure, test the model.

P. 14
CHAPTER 01 / THE MODEL IS NOT THE WORLD

The first description of a problem is not necessarily the problem.

Before code exists, an engineer chooses a reduced world. Some entities become objects, some quantities become variables, some relationships become dependencies, and everything else is temporarily omitted.

In ordinary life those choices often happen invisibly. We call a person unreliable, a market bad, a child difficult, or an organization slow and begin reasoning from the label. The label has already compressed observations, assumptions and causal guesses into one representation.

Ask what has been modeled, what has been omitted, and what evidence would distinguish this model from another.

P. 16
STUDY QUESTION

Why can a precise model still produce the wrong answer?

Because precision is conditional on what the representation includes. A model can manipulate its chosen variables correctly while omitting a variable, relation or objective that materially changes the real outcome.

Write two different problem statements for one current problem. What does each frame exclude?

P. 97
CASE 01 / THE RELEASE THAT KEPT SLIPPING

Repeated delay was the output. The hidden structure was upstream.

A software team misses four release dates. Each retrospective blames estimates. A structural audit finds that late legal review repeatedly changes data-retention requirements, forcing architecture changes after implementation.

The better move is not to begin with motivation. Reconstruct the dependency graph, timing and contract boundary, then test whether moving the constraint upstream reduces rework.

Same output. Different producing structure. Different answer.
